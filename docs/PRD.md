# PRD: 숙박·레저 예약+결제 시스템 보일러플레이트

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 작성일 | 2026-08-31 |
| 대상 | 개발팀 / 신규 프로젝트 착수 시 참고 |
| 관련 문서 | `예약결제시스템_DB스키마_API설계.md` |

---

## 1. 개요

### 1-1. 배경
펜션·민박·캠핑장 등 소규모 숙박·레저 사업자를 대상으로 한 예약+결제 시스템 구축 요청이 반복적으로 발생한다. 매 프로젝트마다 예약 캘린더, 재고 동시성 처리, 결제 연동, 관리자 페이지를 처음부터 개발하는 것은 비효율적이다.

### 1-2. 목적
신규 프로젝트 착수 시 **핵심 예약·결제 로직이 이미 구현된 상태로 시작**할 수 있는 Next.js 기반 보일러플레이트를 구축한다. 개별 클라이언트 프로젝트는 이 보일러플레이트를 fork하여 브랜딩·콘텐츠·세부 정책만 커스터마이징한다.

### 1-3. 이 문서의 범위
- 보일러플레이트가 **기본으로 제공해야 하는 기능**과 **프로젝트별로 확장 가능해야 하는 지점(extension point)**을 정의한다.
- 특정 클라이언트의 개별 요구사항(고유 디자인, 특수 프로모션 등)은 다루지 않는다.

---

## 2. 목표 및 성공 지표

| 목표 | 성공 지표 |
|---|---|
| 신규 프로젝트 착수 속도 향상 | 예약/결제 핵심 기능 개발 기간 2주 → 3일 이내 |
| 이중예약·동시성 버그 재발 방지 | DB 제약으로 원천 차단 (애플리케이션 버그와 무관하게 보장) |
| 코드 재사용률 향상 | 신규 프로젝트에서 보일러플레이트 코드 80% 이상 그대로 사용 |
| 유지보수 효율화 | 공통 로직 수정 시 여러 프로젝트에 일괄 반영 가능한 구조 |

## 3. 타겟 사용자

| 구분 | 설명 |
|---|---|
| **최종 사용자 (고객)** | 숙소/캠핑장을 예약하고 결제하는 일반 방문자. PC/모바일 웹 사용, 비회원 예약이 기본 |
| **운영자 (사업주/스태프)** | 예약 현황 확인, 객실·요금 관리, 취소/환불 처리를 하는 관리자 |
| **개발팀 (내부)** | 보일러플레이트를 fork하여 신규 프로젝트를 세팅하는 개발자 — 이 PRD의 실질적 1차 사용자 |

## 4. 범위 정의

### 4-1. 보일러플레이트가 기본 제공하는 것 (In-scope)
- 예약 홀드 → 결제 → 확정의 전체 예약 플로우
- 이중예약 방지 로직 (DB 레벨 제약)
- PG사 연동 추상화 레이어 (특정 PG사에 종속되지 않는 인터페이스)
- 예약/객실/요금 관리자 CRUD 페이지
- 취소/환불 규정 엔진 (일자별 %) 및 자동 계산
- 메일 발송 인터페이스 (연동 어댑터 구조)
- (문자/카카오 알림톡은 v1 범위에서 제외, 추후 별도 개발 예정 — 인터페이스 확장 지점만 대비)
- 예약 상태 자동 만료 배치(Cron)
- 기본 인증(관리자 로그인, Supabase Auth)

### 4-2. 프로젝트별로 커스터마이징하는 것 (Out-of-scope for 보일러플레이트, Extension Point로 제공)
- 브랜딩(로고, 컬러, 폰트, 도메인)
- 객실/사이트 실제 데이터, 사진, 콘텐츠
- 특정 PG사 실연동 키/계약 (인터페이스는 제공, 실 연동은 프로젝트별)
- 특수 프로모션/쿠폰/멤버십 로직
- 다국어 지원 여부 (구조는 대비하되 기본은 한국어 단일)
- 멀티 지점(프랜차이즈형) 지원 여부 — 아래 오픈 이슈 참조

## 5. 기능 요구사항

각 항목은 `사용자 스토리` + `완료 기준(AC)` 형식으로 기술한다.

### 5-1. 예약 (Reservation)

**FR-1. 객실/사이트 조회 및 예약 가능 여부 확인**
- 사용자 스토리: 고객으로서, 원하는 날짜에 예약 가능한 객실과 가격을 확인하고 싶다.
- AC:
  - [ ] 체크인/체크아웃 날짜 선택 시 해당 기간 예약 가능한 객실 타입 목록과 가격이 표시된다.
  - [ ] 성수기/주말 등 요금 정책이 자동 반영된 최종 가격이 표시된다.
  - [ ] 예약 마감된 객실은 "마감" 상태로 명확히 구분 표시된다.

**FR-2. 임시 홀드 생성**
- 사용자 스토리: 고객으로서, 결제를 진행하는 동안 내가 선택한 객실이 다른 사람에게 넘어가지 않길 원한다.
- AC:
  - [ ] "예약하기" 클릭 시 해당 객실·날짜에 대해 홀드가 생성된다.
  - [ ] 홀드 유지시간(기본 10분, 설정 가능)이 지나면 자동으로 재고가 반환된다.
  - [ ] 동시에 같은 객실·날짜를 시도한 두 번째 사용자는 명확한 오류 메시지를 받는다.
  - [ ] 홀드 유지시간은 프로젝트별 환경설정 값으로 변경 가능해야 한다.

**FR-3. 예약 확정 (즉시확정 모델)**
- 사용자 스토리: 고객으로서, 결제가 완료되면 별도 승인 없이 예약이 바로 확정되길 원한다.
- AC:
  - [ ] 결제 성공 웹훅 수신 시 예약 상태가 자동으로 '확정'으로 전환된다.
  - [ ] 확정 즉시 고객에게 알림(메일)이 발송된다.
  - [ ] 승인제(관리자 확인 후 확정)로 정책을 바꿀 수 있는 확장 지점이 코드에 존재해야 한다. *(v1은 즉시확정만 구현, 승인제는 인터페이스만 대비)*

**FR-4. 예약 조회 및 취소 (고객)**
- 사용자 스토리: 비회원 고객으로서, 예약번호와 연락처만으로 내 예약을 조회하고 취소하고 싶다.
- AC:
  - [ ] 예약번호+전화번호 조합으로 인증 없이 예약 상세를 조회할 수 있다.
  - [ ] 취소 요청 시 환불 규정에 따른 환불 금액이 자동 계산되어 사전 안내된다.

### 5-2. 결제 (Payment)

**FR-5. PG 연동 추상화**
- 사용자 스토리: 개발자로서, PG사를 교체하더라도 핵심 로직을 다시 짜지 않아도 되길 원한다.
- AC:
  - [ ] `PaymentProvider` 인터페이스(결제요청/웹훅검증/환불)를 정의하고, 최소 1개 PG사(예: 토스페이먼츠) 구현체를 기본 제공한다.
  - [ ] 신규 PG사 추가 시 인터페이스 구현만으로 확장 가능해야 한다.

**FR-6. 결제 웹훅 처리 (멱등성)**
- AC:
  - [ ] 동일 결제 건에 대한 웹훅이 중복 수신되어도 예약이 중복 확정되지 않는다.
  - [ ] 홀드가 만료된 이후 결제가 완료된 예외 케이스에서 자동 환불 처리가 트리거된다.

**FR-7. 환불 처리**
- AC:
  - [ ] 환불 규정 테이블 기반으로 환불 금액이 자동 계산된다.
  - [ ] 관리자가 규정과 다른 금액으로 수동 환불할 수 있는 예외 처리 경로가 존재한다.

### 5-3. 관리자 (Admin)

**FR-8. 예약 관리**
- AC:
  - [ ] 예약 목록을 상태/기간별로 조회할 수 있다.
  - [ ] 예약 강제 취소 및 수동 환불 처리를 할 수 있다.

**FR-9. 객실/요금 관리**
- AC:
  - [ ] 객실 타입, 개별 객실(유닛), 요금 정책(기간/요일별)을 CRUD 할 수 있다.
  - [ ] 특정 객실을 일시적으로 '비활성화(점검중)' 처리할 수 있다.

**FR-10. 대시보드**
- AC:
  - [ ] 오늘/이번주 예약 수, 매출 요약을 확인할 수 있다.

### 5-4. 알림 (Notification)

**FR-11. 알림 발송 어댑터**
- 사용자 스토리: 개발자로서, 알림 채널(메일)을 프로젝트별로 다른 벤더(SMTP, 메일 발송 API 등)로 교체할 수 있길 원한다.
- AC:
  - [ ] `NotificationChannel` 인터페이스를 정의하고, 메일 채널 구현체를 기본 제공한다.
  - [ ] 예약 확정, 취소/환불 등 주요 이벤트 발생 시 고객·운영자에게 메일이 발송된다.
  - [ ] 발송 성공/실패 이력이 `notification_logs`에 기록된다.
  - [ ] 발송 실패 시 재시도 로직 또는 실패 알림(운영자용)이 존재한다.
  - [ ] 문자/카카오 알림톡은 v1 범위에서 제외하며, `NotificationChannel` 인터페이스만으로 추후 채널을 추가할 수 있도록 확장 지점을 열어둔다. *(추후 별도 개발 예정)*

### 5-5. 배치/스케줄러

**FR-12. 홀드 자동 만료**
- AC:
  - [ ] 매 1분 주기로 만료된 홀드를 자동으로 해제하는 배치가 동작한다.
  - [ ] 배치 실행 실패 시 로그가 남고 알 수 있어야 한다(모니터링 연동은 v1 범위 밖, 로그 기록까지만).

## 6. 비기능 요구사항 (NFR)

| 구분 | 요구사항 |
|---|---|
| **동시성** | 동일 객실·기간에 대한 동시 예약 요청 시 DB 제약으로 단 1건만 성공해야 한다 (`EXCLUDE` 제약 필수 적용) |
| **성능** | 예약 가능 여부 조회 API 응답 500ms 이내 (일반 트래픽 기준) |
| **보안** | 카드정보 등 결제 민감정보는 자체 서버에 저장하지 않는다 (PG사 위임) |
| **보안** | 관리자 API는 인증된 세션 + RLS로 property 단위 데이터 격리 |
| **확장성** | 신규 프로젝트는 환경변수/설정값 변경만으로 브랜딩·정책 조정이 가능해야 한다 (코드 포크 최소화) |
| **테스트 가능성** | 동시 예약 충돌 시나리오에 대한 자동화 테스트(통합 테스트)를 보일러플레이트에 포함한다 |
| **관측성** | 결제 실패, 웹훅 처리 실패 등 핵심 실패 지점에 로그를 남긴다 |
| **접근성/디자인** | 보일러플레이트 자체는 최소 스타일(Tailwind 기본)만 제공, 프로젝트별 디자인 시스템은 오버라이드 가능한 구조 |

## 7. 기술 스택 및 아키텍처

- **Frontend/Backend**: Next.js (App Router), TypeScript, Tailwind CSS
- **DB/Auth/Realtime**: Supabase (PostgreSQL)
- **결제**: PG 연동 추상화 레이어 + 어댑터 패턴
- **배치**: Vercel Cron 또는 Supabase Scheduled Functions
- **배포**: Vercel (프로젝트별 별도 배포, DB는 프로젝트별 별도 Supabase 프로젝트 사용을 기본 원칙으로 함 — 멀티테넌시는 오픈 이슈 참조)

폴더 구조 원칙:
```
/app
  /(public)          # 고객용 페이지
  /admin             # 관리자 페이지
  /api               # Route Handlers
/lib
  /payments          # PaymentProvider 인터페이스 + 구현체
  /notifications     # NotificationChannel 인터페이스 + 구현체
  /reservations      # 홀드/확정/취소 핵심 로직 (도메인 레이어, PG/알림과 분리)
/supabase
  /migrations        # DB 스키마 마이그레이션 (버전관리 필수)
  /seed.sql           # 샘플 데이터
```

> 핵심 원칙: **예약 도메인 로직(`/lib/reservations`)은 PG사·알림 채널 구현체에 직접 의존하지 않는다.** 인터페이스를 통해서만 접근하여, 신규 프로젝트에서 PG사/알림 채널을 교체해도 도메인 로직은 수정하지 않는다.

## 8. 데이터 모델 & API

상세 스키마와 엔드포인트 명세는 `예약결제시스템_DB스키마_API설계.md` 문서를 기준으로 한다. 보일러플레이트 관점에서 추가로 지켜야 할 원칙:

- 모든 마이그레이션은 `supabase/migrations`에 버전 관리되며, 신규 프로젝트는 이 마이그레이션을 그대로 적용하는 것에서 시작한다.
- 프로젝트별 커스텀 필드가 필요한 경우, 기존 테이블 컬럼을 직접 변경하지 않고 `metadata jsonb` 컬럼(각 핵심 테이블에 기본 포함)을 우선 활용한다.

## 9. 마일스톤 (보일러플레이트 자체 개발 기준)

| 단계 | 내용 | 산출물 |
|---|---|---|
| M1 | DB 스키마 확정 및 마이그레이션 작성 | `supabase/migrations` |
| M2 | 예약 홀드/확정/만료 핵심 도메인 로직 구현 + 동시성 테스트 | `/lib/reservations` + 테스트 코드 |
| M3 | PG 연동 추상화 + 1개 PG사 구현체 | `/lib/payments` |
| M4 | 고객용 예약/결제 화면 (기본 스타일) | `/app/(public)` |
| M5 | 관리자 페이지 (예약/객실/요금 관리) | `/app/admin` |
| M6 | 알림 어댑터 + 배치(Cron) | `/lib/notifications`, Cron 설정 |
| M7 | 문서화 (신규 프로젝트 세팅 가이드, README) | `README.md`, `SETUP.md` |

| **멀티테넌시 여부** | 여러 클라이언트를 하나의 Supabase 프로젝트/DB로 운영할지, 프로젝트별로 완전히 분리할지 결정 필요. 분리가 단순하지만 인프라 비용↑, 통합이 복잡하지만 운영 효율↑ | M1 착수 전 | 여러 클라이언트는 프로젝트별로 완전히 분리하여 각각의 Supabase 프로젝트/DB로 운영
| **PG사 표준화** | 어떤 PG사를 1차 기본 구현체로 삼을지 (수수료, 문서화 수준, 웹훅 안정성 고려) | M3 착수 전 | 토스페이먼츠 결제창 일반 결제 (보일러플레이트는 실제 PG사와 실연동하지 않고 테스트 모드로 진행)
| **승인제 확장 가능성** | 즉시확정 외 승인제 예약이 필요한 클라이언트가 나올 경우를 대비한 상태 머신 확장성 | M2 설계 시 |
| **디자인 시스템 분리 수준** | Tailwind 기본 컴포넌트만 둘지, 최소한의 공통 UI 컴포넌트 라이브러리까지 포함할지 | M4 착수 전 |
